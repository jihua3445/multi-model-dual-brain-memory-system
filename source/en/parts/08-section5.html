05 · Runtime Loops

The Six Runtime Loops

The three online loops handle "now"; the three offline loops handle "later".

Whether a memory system is really "working" depends not on how many tables it has, but on whether it has stable closed loops: whether input can be encoded correctly, whether a cue can recall the right fragments, whether a better decision can be made after recall, whether action outcomes can be written back, whether experience can be distilled into knowledge at night, and whether old information can be safely forgotten or updated. There are six loops, and none of them is dispensable.

5.1 Encoding loop: from perceptual stream to events

  1. Segment.Use prediction-error peaks, goal switches, scene changes, and topic turns to cut the continuous perceptual stream into candidate events. Over-fine segmentation fragments the record; over-coarse segmentation loses detail. The default unit is "one nameable episode".
  2. Score salience.salience = σ(w·[novelty, goal_relevance, social_impact, |valence|, prediction_error, explicit]). Events scoring below the threshold enter a short-TTL buffer and are not immediately allocated a long-term engram.
  3. Resolve identity.Faces, voiceprints, forms of address, and context jointly produce person candidates; when uncertain, keep candidates rather than forcing an identification. An identity error contaminates the entire relationship chain, so it is better to ask one more question.
  4. Write the event.Write to an immutable event log: time, scene, participants, action, outcome, source, status. Actions must be structured (who did what to whom), not merely a paragraph of summary.
  5. Allocate an index.Generate a sparse code and association edges: person, place, topic, goal, affect, causes and consequences. The index stores only pointers and weights, never a copy of the full text.
  6. Three derivations.Judge whether this experience yields a knowledge candidate, a skill candidate, or relationship evidence; candidates are not promoted immediately but enter a pending-verification queue.
  7. Working memory.If the event is relevant to the current task, allocate a slot pointer to the ContextPacket; otherwise it remains in long-term storage only.

5.1.1 Executable rules for event segmentation

Event segmentation theory holds that boundaries occur at prediction-error peaks or at goal/scene switches (Zacks & Swallow 2007). In engineering terms, do not use fixed windows; use the OR of four rules:

boundary = (precision * |observed - expected| > θ_pe)
        or topic_changed or person_changed
        or gap_seconds > θ_gap
        or duration_seconds > θ_max

θ_pe comes from the precision-weighted error of 2.4: the larger the error and the higher the precision, the more readily a boundary triggers. θ_gap / θ_max prevent a single conversation from being cut into infinitely many fragments. After segmentation, the event inherits participants, topic, maximum salience, and start time; the text serves only as a summary, while the raw perception is still retained.

Implementation conventionThe "graph" here is not a graph database but a lightweight association index: an adjacency list with 1–2 hop expansion, decaying per hop with a capped budget; it outputs path / hop, and simulated edges are excluded by default. It is used only for candidate expansion and does not replace the original scoring. See runtime/graph_retrieval.py.
Frontier addendumRetrieval is not neutral: goal-directed retrieval temporarily suppresses competing items (retrieval-induced forgetting) and may also facilitate related items; however, direct evidence from 2024–2026 remains limited. The current implementation performs only a reversible, time-limited accessibility penalty: after a hit, competing items on the same topic or involving the same person are multiplied by 0.85 for 3 logical time units (turns by default; seconds in production if configured), restoring when the TTL expires; no evidence is deleted and no relationship is altered.
GuardrailThe encoding stage does not permit "summarizing into facts while writing". Facts and interpretations must be kept separate; a summary may only occupy the summary field and may not replace the raw event.

5.2 Retrieval loop: from cue to ContextPacket

  1. Parse the cue.Extract person, time, place, topic, affect, and goal; determine the query type: fact, experience, relationship, commitment, procedure, or "can't quite say".
  2. Pattern separation.Disambiguate first: two "Boss Zhangs", two "last times", two versions of a contract. When similarity exceeds the threshold but time, scene, or outcome differ, force them into separate candidates and supply the discriminating evidence.
  3. Pattern completion.Perform multiple rounds of expansion over the person–event–relationship graph; vector nearest neighbors supplement semantic similarity; temporal and causal constraints filter. Each round reranks by cue_overlap + association + recency + salience + source_reliability − interference.
  4. Reconstruct.Assemble the candidate fragments into a coherent narrative, annotating each sentence with its source [E102]; state facts and interpretations separately; where uncertain, say explicitly that it is uncertain.
  5. Audit sources.For each sentence check the source type (first-hand / relayed / inferred / generated), the number of supporting evidence items, and whether it conflicts with known records; then give an overall confidence.
  6. Compile the context.Compress the result into 4±1 slots: who, relationship, experiences, goal, commitments, changes, uncertainties. Each slot has a token cap; beyond it, use a summary or switch to a pointer.

Retrieval is not "finding all the relevant documents". It is "selecting the fewest blocks that suffice for this round of thought". If a ContextPacket needs twenty fragments to be intelligible, that usually means the system has not consolidated well, not that the Main Brain needs more context.

5.3 Decision loop: how the Main Brain uses the ContextPacket

  1. Orient.Read the ContextPacket and confirm: who the individual is, who the other party is, what relationship holds between them, what is to be done now, which commitments are outstanding, and what is uncertain.
  2. Choose a mode.If the situation signature hits the habit cache and risk is low, time is tight, and outcomes are stable → take the model-free fast path; otherwise take the model-based slow path. The arbitration authority belongs to the Main Brain, not to the Backend.
  3. Simulate.On the slow path the Main Brain may call future simulation: generate 2–3 candidate scripts from related episodes and compare expected outcomes, risks, and relationship effects; it may also ask the Backend to expand a particular event or verify a particular claim.
  4. Decide.The Main Brain selects an action and writes down the expected outcome (for the later RPE). The decision requires no Backend "approval", and the Backend has no approval authority.
  5. Express / act.Execute through the Effector: speak, send a message, call a tool, make a movement. The Effector only executes; it never initiates on its own.

5.4 Action write-back loop: how outcomes change memory

  1. Observe.Record the actual outcome, the other party's response, side effects, and whether the expectation was met.
  2. Compute RPE.δ = r − V(s); a positive error reinforces the previous step, a negative error weakens it and flags it as "needs re-evaluation".
  3. Update the event.Change the event status from "open" to "closed / to follow up"; append the outcome without overwriting the original record.
  4. Update the relationship.A single interaction counts as only one piece of evidence; the relationship summary aggregates over a sliding window and does not lurch on a single event (unless the impact is extreme).
  5. Update source calibration.On write-back, call record_outcome: confirmation/refutation updates the source's history; the outcome is written as a direct event; a large prediction error triggers a new version of the explanation; the same outcome counts as one piece of relationship evidence only, and repeated write-backs are not double-counted.
  6. Flag for consolidation.Events with high salience, high prediction error, or unresolved commitments enter the nightly consolidation queue.

5.5 Offline consolidation loop: what sleep does

Offline consolidation is not "summarizing today's conversations". It comprises at least five stages:

Table 9 · The five stages of the consolidation batch
StageWhat it doesCorresponding mechanism
ScanTraverse the day's events, ordered by salience × prediction error × goal relevance × degree of incompletionGlobal scanning by slow oscillation
ClusterGroup events by person, project, theme, and time; select representative eventsLocal packing by sleep spindles
ReplayFor each group, replay "cause → action → outcome" and generate counterfactuals and lessonsSequence replay by hippocampal ripples
AbstractExtract schemas, rules, and skill candidates from multiple events; require a sufficient count of independent evidenceSystems consolidation / schema assimilation
Merge and pruneWrite into the semantic graph / skill library; update relationship summaries; decay low-value indexes; compress ordinary interactions into phase summariesSynaptic homeostasis / adaptive forgetting

The priority of consolidation is not "newest first" but "most useful for the future first": events that are high in salience, high in prediction error, tied to unfinished goals, or repeatedly accessed but not yet abstracted are replayed first. Conversely, low-value, repetitive, consequence-free daily interactions should be compressed into phase summaries rather than retained one by one.

5.6 Forgetting and reconsolidation loop: changing the past safely

These two loops are often conflated, but they point in opposite directions: forgetting lowers retrievability, while reconsolidation updates content. They share one trigger: retrieval. Every retrieval records one access but does not add evidence; if the retrieval comes with a significant prediction error or new information, a new version is created; otherwise only the timestamp and accessibility are updated.

# Minimal reconsolidation decision
access_log.append(event_id, timestamp, cue, context)

PE = |expected_outcome − observed_outcome|
novelty = 1 − cos(new_info, existing_summary)

if PE > θ_pe or novelty > θ_novelty:
    new_version = revise(event, new_info, basis=evidence_ids)
    new_version.supersedes = old_version.id
    store.append(new_version)          # does not overwrite the old version
    enqueue_for_consolidation(new_version)
else:
    event.last_accessed = now
    event.access_count += 1            # raises accessibility only; adds no evidence

Forgetting follows the retention formula: R = exp(−Δt / S) × (1 + α|valence|) × (0.5 + 0.5·utility) × relationship_factor. Content below the threshold moves to cold archive; content below a lower threshold and not on the exemption list is removed from the active index. The raw event log is still retained, for auditing and for lawful tracing beyond the "right to be forgotten".

5.7 Coupling between the loops: no single link can be optimized alone

The six loops are not a pipeline but interlocking circuits. Optimizing any single link usually pushes the problem into another:

  • Encoding ↔ retrieval.If no cue is left at encoding time, retrieval will "draw a blank"; patterns of retrieval failure should feed back into the encoding strategy, telling the system "what to record for this kind of event next time".
  • Retrieval ↔ consolidation.Events that are repeatedly accessed but never abstracted are prime candidates for consolidation; conversely, events never accessed and with no future utility should enter cold archive earlier.
  • Consolidation ↔ encoding.The schemas formed by consolidation change the salience of the next encoding: information consistent with the schema is merged faster, while inconsistent information deserves deeper encoding.
  • Forgetting ↔ retrieval.Forgetting reduces interference and makes retrieval more precise; but excessive forgetting makes the system "rediscover" lessons it has already learned. The retention formula and the exemption list are the regulating valve between the two.
Engineering implicationDo not evaluate the system on "retrieval hit rate" alone. A system that optimizes only retrieval will tend to keep everything and refuse to forget; eventually the context becomes dirty and decisions slow down. Loop metrics must come in pairs: recall with precision, retention with false-deletion rate, compression ratio with information loss.
