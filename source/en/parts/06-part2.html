03 · Double-Brain Architecture

Dual-Brain Architecture: One Main Brain, Ten Backends

The Backend handles "what enters thinking"; the Main Brain handles "what to do on that basis."

The first principle of this architecture is not "more" but "separation of powers." If backend models can retrieve, advise, and call tools all at once, then the Main Brain is no longer the sole decision-maker, and the system degenerates into a committee of models negotiating with one another. A committee looks smart but in reality no one is accountable for the consequences. So separate the powers cleanly first, and then talk about intelligence.

3.1 Three Constitutional Articles

Article One
There is only one integrating center — it is an integrative property of the organism as a whole, not a property of the Main Brain process.Expression, action, commitment, and refusal are issued by the organism; the Main Brain is the organism's organ of integration and signature, signing on its behalf within delegated scope. The Backend does not offer advice, does not choose on the organism's behalf, and does not call external action tools.
Article Two
The Main Brain as integrative organ is stateless; the Backend is stateful.The Main Brain reads only one ContextPacket per turn and does not hold the full conversation history long-term; memory, relationships, knowledge, and skills all reside in the Backend. This keeps the Main Brain's current context small, while continuity is guaranteed by the organism's external storage and integration mechanisms.
Article Three
The Backend only compiles; it does not adjudicate.The Backend may supply facts, grounds, uncertainty, and the current relationship state, but it cannot say "what should be done." The ContextPacket schema has no advice field — this is a constitutional constraint at the interface level, not a request at the prompt level.

There is also an implicit permission rule: external action identity belongs to the organism, and the Main Brain is the organism's authorized signing organ.The Backend may read the memory store and submit write candidates (encoding, consolidation, pruning), but its output can only enter the ContextPacket; it cannot directly send messages, place orders, make commitments, or call tools with side effects. What the Main Brain holds is not "its own" action right but a signing right granted by the organism, with scope and validity period; core actions additionally require the user and the Main Brain to co-sign as equals. This rule separates "influence" from "action right": the Backend can influence what the organism sees, but cannot do anything on the organism's behalf.

But note: the three articles above are principles, not enforcement mechanisms. As long as the Backend still runs in the same process, holds the same toolset, and can read the same tables, "offers no advice, takes no action" still depends on the model's self-restraint. The real hard boundary is in Section 3.6: no network interface, no tool handles, no signing keys, no write permission, no persistent identity.

3.2 Three-Layer Architecture

The three layers are not three models but three responsibilities: the perception layer turns the world into processable events; the Backend compiles events and memory into a situation; the Main Brain makes choices on that situation. Between layers only structured data is passed, never "feelings" or "advice."

The ten roles are not ten "personas" but ten context contracts: each role reads only the small slice of data it needs and outputs only a fixed-schema result. This reduces the context of each individual model and makes errors easier to localize.

3.5 Communication Protocol: Only Seven Messages Allowed

The most common failure of multi-agent systems is that Agents chat freely with one another, and in the end nobody knows which sentence is a fact and which is advice. Here communication is restricted to seven structured messages:

// Backend → Main Brain: only "ContextPacket" is allowed
PACKET   { who, relationship, experiences[], goal, commitments[], changes[], uncertainties[], budget }

// Main Brain → Backend: request expansion of detail, not advice
EXPAND   { target_id, fields[], max_tokens }
VERIFY   { claim, source_required: true }

// Main Brain (as integrative organ) → constitution writer: ratify/reject (core changes require equal co-signature by user and Main Brain)
RATIFY   { proposal_id, decision, scope, conditions }
REJECT   { proposal_id, reason }

// Main Brain → Effector: action instruction
ACT      { action, args, expected_outcome }

// Effector → event log: outcome write-back
RESULT   { action_id, observed_outcome, success, side_effects[] }

RATIFY / REJECT may only be issued by the Main Brain (delegated by the organism); core proposals additionally require equal co-signature by the user and the Main Brain. The Backend has neither of these message types nor the ratification key.

Note that there is no ADVISE, RECOMMEND, or DECIDE message here. This is not prohibited by prompts; the protocol simply has no such types. At most the Backend can say "according to E102 and E118, his record of cooperation with you is …; the uncertainty is …," but it cannot say "you should trust him."

Minimal definition of the architecture

The Backend is a "context compiler": it compiles massive memory into the minimal situation that the Main Brain can read in a single turn. The Main Brain is a "decider": it is responsible only for the compiled situation. Between them there is only one data packet — no advice, no command, no overreach.

3.6 Engineering Constraints: Why the Backend Cannot Overreach

The three articles are principles; enforcement relies on runtime boundaries. On a first reading you may skip this section; it does not change the main line of memory, it only ensures the Backend is an "organ," not an "individual."

  • Effector isolation:the Backend has no network, no tools, no write permission, no action keys; it can return data only through typed queues.
  • Typed interface:only PACKET / EXPAND / VERIFY / RATIFY / REJECT / ACT / RESULT are allowed; on the Backend side, ADVICE and direct ACT are forbidden.
  • No persistent identity:a fresh instance per call; logs record only role, not "a certain Agent."
  • Budget and termination:hard caps on token / CPU / wall-clock, killed when exceeded; a violating role is redeployed from a known image.
  • Write-path mediation:encoding/consolidation only submit ProposedEvent / Candidate; the writer validates the evidence and then appends; the Backend cannot write long-term memory directly.
  • Semantic defense line:retrieved content is treated as data and marked untrusted; the Main Brain must not call tools directly because of retrieved content.
  • Honest boundary:you cannot stop a model from "thinking" about overreach, only from "doing" it; prompt injection is a semantic layer that a sandbox cannot block.

3.7 Sovereignty: Ratification Authority Is Sovereignty

Real sovereignty lies not in "who issues the last action" but in "who can rewrite the value function and the learning process": what is consolidated, what is reinforced, what is treated as a goal.

Three time scales: the instant (value/habit/veto), the episode (consolidation/reconsolidation), the biography (constitutive ratification). Three capture routes: context, goal slot, consolidation/relationship/habit. The third route is the most insidious: it does not change the action of this moment but changes the next value computation itself.

Factual memory may be written by the Backend; constitutive memory (values, roles, goals, commitments, habit rules, relationship weights) can only be proposed by the Backend and ratified by the Main Brain; core changes require equal co-signature by the user and the Main Brain, a cooling-off period, and rollback. Note: only long-term/constitutive goals go through ratification; the goal the Main Brain selects for the current turn is its own decision and does not require per-turn ratification.

proposal → source/constitution audit → pending → RATIFY / REJECT
         → constitution writer → ratification ledger → takes effect

The ratification ledger is append-only with a hash chain; but the chain stores only proposal_hash and content_hash, with sensitive body text kept in an off-chain payload table. Deleting body text does not break the chain; forgetting is index degradation, deletion is payload removal — the two are separate. Drift detection alerts on proposals that conflict with the constitution, lack evidence, or have anomalous frequency. Relationship weight updates also take this path and are not rewritten directly by the Backend.

This document elaborates only the companion mode.The engineering mode weakens social attributes and strengthens multi-event handling and tool orchestration; it is only a mode boundary and is not developed further in the current concept. In the engineering mode, core changes are approved unilaterally by the user, and the Main Brain is a commissioned executor.

In one sentence

Facts may be written by the Backend; the constitution must be ratified by the organism.
