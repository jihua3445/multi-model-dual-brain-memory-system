07 · Context Economy

Multi-Model Division of Labor and Context Economy

The key to saving context is not writing shorter prompts, but letting each model face only its own small slice of the world.

“Multi-agent” is often misunderstood as “several models discussing together.” If every model reads the same long context and then forwards it to the others, costs go up and noise goes up. Real division of labor is splitting context by schema: person identification looks only at face, voice, and form of address; retrieval looks only at cues and indexes; relationship judgment looks only at event summaries; the Main Brain sees only 4±1 slots. Across layers, only a single ContextPacket is passed, instead of copying the whole conversation ten times.

7.1 Why several models instead of one larger model

Context isolation
Each backend role reads only the fields it needs, reducing its input from “the whole conversation” to “a single structured slice.” This saves tokens and reduces interference from irrelevant information in judgment.
Capability specialization
Person identification suits small multimodal models, salience suits classifiers, retrieval suits embeddings plus graph algorithms, and only the Main Brain needs a large model. Using a large model for everything wastes both cost and latency.
Parallelism
Perception, retrieval, and relationship judgment can run simultaneously; the Main Brain waits at only one convergence point: the ContextPacket. The critical path changes from “ten serial steps” to “three parallel branches plus one compilation.”
Fault isolation
If retrieval is wrong, source auditing can stop it; if relationship judgment drifts, the Main Brain can see the evidence and the uncertainty. When one giant model errs, the entire answer usually errs with it.
Replaceability
Each role has a fixed input/output schema, so its model, vendor, or version can be swapped independently without rewriting the whole system.

7.3 The context contract

Every Agent must have a “context contract”: input fields, output schema, max tokens, timeout, and fallback on failure. This matters more than a “role prompt,” because it turns “you should only look at these fields” into a system constraint.

AgentContract {
  name, role,
  input_schema,            # only these fields may enter context
  output_schema,           # structured output; free text rejected
  max_input_tokens,
  max_output_tokens,
  timeout_ms,
  fallback,                # returns "unknown" on failure; never fabricates
  permissions: read | write | act
}

For example, the input to the person identification Agent is only face/voiceprint features, form of address, and the time and place of the most recent appearance; it cannot see the full conversation, nor does it need to know contract terms. The relationship judgment Agent sees only event summaries and relationship dimensions relevant to the current person, and does not need to see all project documents. Each model's context is thus small, and “what it should see” is designed rather than left to chance.

7.4 Parallelism, caching, and lazy expansion

The online critical path can be drawn as a DAG: perception and identity recognition in parallel; once identity is fixed, retrieval and relationship judgment in parallel; the two converge at context compilation; only after compilation does the Main Brain start. Source auditing can run after compilation and before the Main Brain, or as a “post-hoc audit” after the Main Brain generates.

The two branches at T1 can run in parallel; so can the two at T2; T3 is the only convergence point. Source auditing can be placed after T3 (pre-audit) or after T5 (post-audit): the former is safer, the latter has lower latency.

Caching. Person profiles, relationship summaries, frequently used event indexes, and embedding vectors can all be cached; repeated queries for the same person/project need not be recomputed each time. Cache invalidation is triggered by event writes, not by a fixed TTL.

Lazy expansion. The ContextPacket gives only “one sentence + a pointer”; when the Main Brain needs detail it issues EXPAND. This turns “pull everything at once” into “paginate on demand,” which saves tokens and keeps the Main Brain's attention on the current problem.

7.5 Cost model: where the savings are

Suppose a monolithic system stuffs 50 turns of history (about 30k tokens) into a large model every round; in the multi-model design, the Main Brain reads only a 1k ContextPacket plus a 2k system prompt per round, while the ten backend branches average 2k tokens each and mostly run in parallel. Roughly, total tokens per round are not necessarily lower (the backend still has to run), but large-model tokens drop sharply, latency is spread out by parallelism, and retrieval quality is higher. The real savings come from three things:

  • Use small models for classification/extraction. Salience, person identification, and source tagging do not need a large model.
  • Use structure instead of raw text. Event records, relationship summaries, and sparse indexes are an order of magnitude shorter than the full conversation.
  • Trade offline for online. Consolidation, abstraction, and deduplication are moved to nightly batch processing; online does only retrieval and compilation.
CounterintuitiveA multi-model system may have higher total tokens than a monolithic system, but “the tokens the Main Brain must read each round” is lower and decision quality is steadier. The optimization target is not the fewest total tokens, but the lowest cost per unit of decision quality.

7.6 How this differs from existing memory architectures

Placing this proposal within the existing lineage of “large-model memory” makes the differences clearer. Most of them solve “how to retrieve relevant text,” whereas this proposal solves “how memory is formed, how it changes, how it is trusted, and how it serves decisions.”
