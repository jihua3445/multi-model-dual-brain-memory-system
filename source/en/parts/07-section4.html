04 · Data Model

Data Model: Events, Persons, Relationships, Interpretations

The first table of a memory system determines what questions it can ask later.

If the system stores only "conversation fragments + vectors," it can only answer "which passage is most similar." If it stores "events + persons + participation + relationships + interpretations," it can answer "what did he promise last time we met," "is there evidence for the individual's judgment about him," and "are this matter and that matter the same one." The data model is not an implementation detail; it sets the cognitive ceiling of the system.

4.1 Event: The Atomic Unit of Memory

An event is not a single utterance, nor a whole day. It is a bounded experience with participants, a course, and an outcome. Event segmentation can be detected from peaks of prediction error, goal switches, scene changes, and turning points in the topic of conversation. An event record should contain at least the following fields:

4.2 Person, Participation, Relationship: Three Tables, Not One

A person profile answers "who he is"; a participation record answers "what he did in this matter"; a relationship summary answers "what relationship we have now." The reason to keep them apart is simple: a person can take part in many events, a relationship can be supported by many events, but a single interaction does not directly equal a relationship.

Table 7 · Person / Participation / Relationship
ObjectKey fieldsDesign point
Personperson_id, forms of address/aliases, identification cues (face/voiceprint/address), known traits, first/last appearanceKeep candidates when identity is uncertain; do not force a merge
Participationperson_id, event_id, role, action, response, co-occurrence vs. actual interaction, source, confidence"In the same frame" is not "interacting"; "he said" is not "he did"
RelationshipFamiliarity, closeness, trust scope, cooperation, commitment, boundaries, social role; each dimension with value, evidence_event_ids, scope, confidence, updated_at"The individual trusts him" and "he trusts the individual" are separate; judgments carry their basis

A relationship is multidimensional, not a single "good/bad" axis. One person may be "high work trust, low personal closeness, good commitment record, strong boundaries"; another may be "high closeness, low trust, average cooperation." Collapsing a relationship into one score discards the most useful information. Every dimension must have evidence events, scope of applicability (work/family/public), and update time; a judgment without evidence can only be labeled speculation.

4.3 Interpretation Layer: Facts and Interpretations Separated, Interpretations Correctable

"He did not reply to the request" is an event; "he does not care" is an interpretation. Mix the two and the system will fossilize a single act into a person's essence. The interpretation layer is stored separately and contains at least:

Interpretation {
  interpretation_id,
  target_event_id,
  perspective: self | other,
  type: feeling | speculation | attribution | evaluation,
  content,
  confidence,              // 0–1, not a true/false binary
  basis_event_ids: [],     // which events support this interpretation
  created_at, updated_at,
  supersedes: interpretation_id | null,
  status: active | revised | retracted
}

Key rule: interpretations may be revised but must not overwrite history. When new information arrives, create a new version that points to the old version being revised; the old version is retained for auditing "why we thought so at the time." This is not only more honest but also more useful: it lets the system explain changes in its own judgments instead of pretending it was always smart.

4.4 Knowledge, Memory, Skill: Three Accumulations from the Same Events

Table 8 · Three accumulations plus the habit cache
TypeAnswersFieldsPromotion condition
MemoryWhat one has experiencedEvent log + person/participation/relationship + interpretation versions; shared event_idEstablished as soon as the event is written; not promoted to "knowledge"
KnowledgeWhat one knowsConcepts/relations/rules, source event_ids, confidence, domain of applicabilitySupported by at least 2–3 independent events; not contradictory to existing schemas
SkillWhat one knows how to doSteps, preconditions, postconditions, caveats, success rate, sourceAt least 2 successes + 1 failure/correction, or expert confirmation
HabitWhat one did last time in a similar situationContext signature, cached template/skill ID, status (candidate / ratified / revoked), proposed_by, ratified_by, frequency, success rate, last used, rollback_toHigh-frequency repetition + stable outcome; the Backend only proposes, the Main Brain ratifies; caches templates only, never decisions

Memory is the direct record of events and relationships; knowledge is a rule abstracted from multiple events; skill is a procedural sequence. All three share the same event_id but are updated separately. Habit is not a fourth kind of accumulation but a cache of high-frequency paths; it only accelerates context assembly and does not replace memory, knowledge, or skill.

"One success is not enough to form a stable skill, and one subjective judgment should not directly become certain knowledge." This constraint from version one should be written into the promotion rules rather than left to the model's self-restraint. It is also the last gate preventing the system from mistaking accident for regularity.

4.5 ContextPacket: The Only Cross-Layer Interface

The ContextPacket is not a "summary" but the minimal situation tailored for the current decision. Its slot count is hard-limited to 4±1, and each slot has a type, content, source, confidence, and TTL. Recommended schema:

ContextPacket {
  packet_id, turn_id, created_at, expires_at,
  governance_mode: companion | engineering,
  self: {
    ratified: { values[], role, long_term_goals[], active_commitments[] },
    pending: [ { proposal_id, type, summary, evidence_count, expires_at } ]
  },
  who: { person_id, name, identity_confidence, candidates[] },
  relationship: {
    dimensions: { familiarity, closeness, trust_scope, cooperation,
                  commitment, boundaries, social_role,
                  social_safety, belonging_need },
    basis_event_ids[], scope, confidence, updated_at
  },
  experiences: [
    { event_id, one_line, why_relevant, source, confidence }
  ],
  omitted: { count, topics[], event_ids[] },   // candidates filtered out
  scene: { place, activity, time, atmosphere },
  goal: {
    current, priority, success_criteria,
    scope: turn | constitutional,   // only constitutional requires ratification
    provenance: { proposed_by, ratified_by, ratified_at, proposal_id },
    lock: none | dual_ratified | user_sovereign | constitutional   // applies only to constitutional
  },
}
// constitutive read-only pointer and remaining slots
ContextPacket (cont.) {
  constitution_ref: { version, ledger_head },
  commitments: [ { content, due, status, counterpart } ],
  changes: [ { what_changed, since_when, source } ],
  uncertainties: [ { question, candidates[], evidence_needed } ],
  affect: { valence, arousal, confidence },
  state_view: {
    goal_pressure, relationship_strain, resource_load, uncertainty,
    unresolved_commitments, impact_gap
  },
  state_params_ref: { schema_version, params_version, state_hash },   // params live in runtime, not in context
  budget: {
    slots: 4, header_tokens: 300, slot_tokens: 600,
    tokens: 900, detail_level: brief|standard|deep
  }
}

This schema has no advice, no recommendation, and no action. It does not "give the Main Brain ideas" but "prepares the facts, relationships, goals, and uncertainties the Main Brain needs to know." The Main Brain may request EXPAND(event_id) to expand details and may request VERIFY(claim) to check sources; but it cannot ask the Backend to "decide for it."

4.6 Evidence Ledger: Repeated Recollection Is Not Multiple Pieces of Evidence

The error that large-model memory systems most easily make is "self-reinforcement": the same summary is repeatedly retrieved and repeatedly rewritten until the system believes it is supported by many independent sources. The human brain has a similar problem: repeatedly recalling an event raises its accessibility but does not turn it into multiple independent experiences. The remedy is an evidence ledger:

  • Evidence is counted by event_id, not by retrieval count.evidence_count = distinct(event_id); an event recalled a hundred times is still one piece of evidence.
  • Source stratification:firsthand > primary document > relayed by another > inferred > model-generated. A higher layer may override a lower one, but the original source must be retained.
  • Interpretation and fact kept in separate accounts:the confidence of an interpretation cannot rise because it has been "cited many times," only because "new independent events have appeared."
  • Contradictions are not averaged:both conflicting records are kept and marked contradicts; retrieval returns both so the Main Brain sees the conflict, rather than the system secretly picking one.
In one sentence The credibility of a memory system does not depend on how fluently it remembers, but on whether it can put a checkable event ID behind every assertion.
