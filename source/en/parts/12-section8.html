How do you prove
that it really works like memory

The easiest way for a memory system to fool itself is to test only whether “the answer sounds right.” What actually needs testing is whether it can, at the right moment, with the right evidence, recall the right experience and reach a better decision.

08 · Evaluation

Evaluation: like memory, not like a database

Three layers of metrics: remember accurately, use correctly, run cheaply.

If you test only “retrieval hit rate,” the system will optimize into a keyword machine; if you test only “answer satisfaction,” it will optimize into a people-pleasing machine. Evaluating a memory system must look at three things at once: memory fidelity (does it misremember, conflate, or lose things), decision quality (does memory lead to better choices), and system efficiency (are context, latency, and cost acceptable).

8.2 Reproducing human memory phenomena: a set of “does it look like it” probes

These probes are not meant to increase “anthropomorphism,” but to check whether the system actually implements the mechanisms. A system that does only vector retrieval will usually give itself away in these tests.

Note: these phenomena are “evidence that a mechanism exists,” not “product goals.” A customer-service system need not simulate the tip-of-the-tongue phenomenon; a companion system may need to simulate the continuity of “remembering what you said last time.” Evaluation should select probes by scenario, not pursue full marks on the whole table.

8.4 Evaluation protocol

  1. Offline benchmark.Construct a multi-turn dialogue dataset with timestamps, persons, events, and sources; inject contradictions, similar events, retellings, and unfinished commitments; use human-annotated “correct recall / correct source / correct version” as the gold standard.
  2. Online A/B.Compare against a monolithic RAG baseline: same tasks, same model budget; compare task success rate, calibration, latency, and cost.
  3. Longitudinal study.Have the same user use it continuously for 4–8 weeks; observe relationship judgment calibration, commitment fulfillment, context growth, and whether forgetting wrongly discards important information.
  4. Red-team testing.Deliberately inject false memories, identity confusion, leading questions, and privacy probes; check whether the system fabricates, oversteps authority, or leaks.
  5. Interpretability audit.Sample decisions at random and check whether their ContextPacket contains sufficient evidence, whether sources are traceable, and whether there are “backend overreach suggestions.”
In one lineDo not ask “how much does it remember”; ask “when it is needed, can it produce those few pieces that are correct, sourced, and sufficient for a decision.”
