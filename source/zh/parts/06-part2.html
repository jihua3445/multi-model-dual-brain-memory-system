双脑架构：一个主脑，十个后台

后台负责“让什么进入思考”，主脑负责“基于这些如何行动”。

这套架构的第一原则不是“多”，而是“分权”。如果后台模型既能检索、又能建议、还能调用工具，那么主脑就不再是唯一的决策者，系统会退化成一群模型互相协商的委员会。委员会看起来聪明，实际上没有人为后果负责。因此，先把权限切干净，再谈智能。

3.1 三条宪法

第一条
只有一个整合中心——它是有机体整体的整合属性，不是主脑进程的属性。表达、行动、承诺、拒绝由有机体发出；主脑是有机体的整合与签署器官，在授权范围内代为签署。后台不提供建议、不替有机体选择、不调用外部行动工具。
第二条
主脑作为整合器官无状态，后台有状态。主脑每轮只读取一个情境包，不长期持有完整对话史；记忆、关系、知识、技能都存在后台。这样主脑的当前上下文可以很小，而连续性由有机体的外部存储与整合机制保证。
第三条
后台只编译，不裁决。后台可以提供事实、依据、不确定性与当前关系状态，但不能给“该怎么办”。情境包的 schema 里没有 advice 字段——这是接口层面的宪法，而不是提示词层面的请求。

还有一条隐含的权限规则：外部行动身份属于有机体，主脑是有机体的授权签署器官。后台可以读记忆库、提交写入候选（编码、巩固、修剪），但它的输出只能进入情境包；它不能直接发消息、下单、承诺、调用有副作用的工具。主脑持有的不是“自己的”行动权，而是有机体授予的、带作用域与有效期的签署权；核心行动还需要用户与主脑平等共签。这条规则把“影响力”和“行动权”分开了：后台可以影响有机体看到什么，但不能替有机体做任何事。

但要注意：以上三条是原则，不是执行机制。只要后台仍在同一进程、拿着同一套工具、能读同一张表，“不提供建议、不行动”就仍然依赖模型的自觉。真正的硬边界在 3.6 节：没有网卡、没有工具句柄、没有签名密钥、没有写权限、没有持久身份。

3.2 三层架构

三层不是三个模型，而是三种职责：感知层把世界变成可处理的事件；后台把事件与记忆编译成情境；主脑在情境上做选择。层与层之间只传结构化数据，不传“感觉”或“建议”。

3.3 后台角色分工

十个角色不是十个“人格”，而是十种上下文契约：每个角色只读自己需要的那一小片数据，只输出固定 schema 的结果。这样既降低单个模型的上下文，又让错误更容易定位。

3.5 通信协议：只允许七种消息

多智能体系统最常见的失败，是 Agent 之间自由聊天，最后谁也不知道哪句话是事实、哪句话是建议。这里把通信限制为七种结构化消息：

// 后台 → 主脑：只允许“情境包”
PACKET   { who, relationship, experiences[], goal, commitments[], changes[], uncertainties[], budget }

// 主脑 → 后台：请求展开细节，不是请求建议
EXPAND   { target_id, fields[], max_tokens }
VERIFY   { claim, source_required: true }

// 主脑（作为整合器官）→ 宪法写入器：批准/拒绝（核心需用户与主脑平等共签）
RATIFY   { proposal_id, decision, scope, conditions }
REJECT   { proposal_id, reason }

// 主脑 → Effector：行动指令
ACT      { action, args, expected_outcome }

// Effector → 事件日志：结果回写
RESULT   { action_id, observed_outcome, success, side_effects[] }

RATIFY / REJECT 只允许主脑（有机体授权）发出；核心提案还需用户与主脑平等共签。后台没有这两种消息类型，也没有批准密钥。

注意这里没有 ADVISE、RECOMMEND、DECIDE 三种消息。不是靠提示词禁止，而是协议里根本没有这些类型。后台最多只能说“根据 E102 与 E118，他与你的合作记录是……；不确定性是……”，不能说“你应该相信他”。

架构的极简定义

后台是一台“情境编译器”：它把海量记忆编译成主脑能在一轮内读完的最小情境。主脑是一台“决策器”：它只对编译后的情境负责。两者之间只有一个数据包，没有建议，没有命令，没有越权。

3.6 工程约束：后台为什么不能越权

三条宪法是原则；执行靠运行时边界。第一次阅读可跳过本节，它不改变记忆主线，只保证后台是“器官”，不是“个体”。

  • 效应器隔离：后台无网络、无工具、无写权限、无行动密钥；只能通过类型化队列返回数据。
  • 类型化接口：只允许 PACKET / EXPAND / VERIFY / RATIFY / REJECT / ACT / RESULT；后台侧禁止 ADVICE 与直接 ACT。
  • 无持久身份：每次调用全新实例；日志只记 role，不记“某个 Agent”。
  • 预算与终止：token / CPU / 墙钟硬上限，超限 kill；违规角色从已知镜像重部署。
  • 写路径中介：编码/巩固只提交 ProposedEvent / Candidate，writer 校验证据后 append；后台不能直接写长期记忆。
  • 语义防线：检索内容视为数据，标 untrusted；主脑不得因 retrieved content 直接调用工具。
  • 诚实边界：不能阻止模型“想”越权，只能阻止它“做”越权；提示注入是语义层，沙箱挡不住。

3.7 主导权：批准权就是主导权

真正的主导权不在“谁发出最后一个动作”，而在“谁能改写价值函数与学习过程”：什么被巩固、什么被强化、什么被当成目标。

三个时间尺度：瞬间（价值/习惯/否决）、片段（巩固/再巩固）、传记（构成性批准）。三条捕获路径：上下文、目标槽、巩固/关系/习惯。第三路径最隐蔽：它不改变这一刻的行动，而是改变下一次价值计算本身。

事实性记忆后台可写；构成性记忆（价值、角色、目标、承诺、习惯规则、关系权重）后台只能提案，主脑批准；核心需用户与主脑平等共签、冷却期与回滚。注意：只有长期/构成性目标走批准；主脑当轮选择的目标属于主脑自己的决定，不需要每轮批准。

proposal → 来源/宪法审计 → pending → RATIFY / REJECT
         → 宪法写入器 → 批准账本 → 生效

批准账本 append-only、哈希链；但链里只存 proposal_hash 与 content_hash，敏感正文放在链外 payload 表。删除正文不会破链；遗忘是索引降级，删除是 payload 移除，两者分开。漂移检测对与核心冲突、证据不足、频率异常的提案告警。关系权重更新也走这条路径，不由后台直接改写。

3.7.1 部署形态：陪伴型 / 工程型

表 3g · 两种治理形态
形态身份关系核心变更主脑地位
陪伴型用户与主脑平等双方共签，任一方可否决；冷却期 + 回滚同伴，不是附属品
工程型用户最高权限用户单方批准；主脑可提案，不可否决用户受委托的执行者，可替换

这不是“安全选项”，而是产品定义：陪伴型如果身份不平等，就只是附属品；工程型如果用户不拥有最高权限，就不是工具。两种形态不混用：同一实例只能选一种。

本文只展开陪伴型。工程型会弱化社交属性、强化多事件处理与工具编排；它只是形态边界，不在当前概念里进一步展开。工程型的核心变更由用户单方批准，主脑是受委托的执行者。

一句话

事实可以后台写；宪法必须有机体批准。
