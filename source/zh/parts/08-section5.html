05 · Runtime Loops

六个运行闭环

在线三环负责“此刻”，离线三环负责“以后”。

一个记忆系统是否真的在“工作”，不看它有多少张表，而看它有没有稳定的闭环：输入能不能被正确编码，线索能不能召回正确的片段，召回后能不能做出更好的决定，行动结果能不能回写，夜里能不能把经验蒸馏成知识，旧信息能不能被安全地遗忘或更新。六个闭环，缺一不可。

图 2 · 记忆生命周期
01 ENCODE · 在线感知 → 候选事件 → 显著性门控 → 事件日志 / 索引
↓
02 CONSOLIDATE · 离线扫描 → 聚类 → 重放 → 抽象 → 合并 / 修剪
↓
03 RETRIEVE · 在线线索 → 模式分离 / 完成 → 重建 → 来源审计 → 情境包
↓
04 DECIDE · 在线主脑读包 → 快路 / 慢路 → 选择 → 写下预期结果
↓
05 ACT · 在线表达 / 工具 / 载体 → 观察结果 → 回写事件
↓
06 RECONSOLIDATE / FORGET · 在线+离线版本化更新 或 衰减 / 冷归档
在线闭环：01 → 03 → 04 → 05 → 06；离线闭环：02 在夜间或空闲时运行，读取 01/05 的事件，反哺 03 的检索质量。06 不是终点，而是下一轮 01 的输入。

5.1 编码闭环：从感知流到事件

  1. 分段。用预测误差峰值、目标切换、场景变化、话题转折把连续感知切成候选事件。分段过细会碎片化，过粗会丢细节；默认以“一个可命名的情节”为单位。
  2. 显著性打分。salience = σ(w·[novelty, goal_relevance, social_impact, |valence|, prediction_error, explicit])。分数低于阈值的事件进入短 TTL 缓冲，不立即分配长期印迹。
  3. 身份解析。人脸、声纹、称呼、上下文共同给出人物候选；不确定时保留 candidates，不强行认定。身份错误会污染整条关系链，宁可多问一句。
  4. 事件写入。写不可变事件日志：时间、场景、参与者、动作、结果、来源、状态。动作要结构化（谁对谁做了什么），不能只写一段摘要。
  5. 索引分配。生成稀疏码与关联边：人物、地点、话题、目标、情绪、前因后果。索引只存指针与权重，不复制全文。
  6. 三类派生。判断这次经历是否产生知识候选、技能候选、关系证据；候选不立即晋升，先进入待验证队列。
  7. 工作记忆。如果事件与当前任务相关，给情境包分配一个槽位指针；否则只留在长时存储。

5.1.1 事件分割的可执行规则

事件分割理论认为，边界出现在预测误差峰值或目标/场景切换处（Zacks & Swallow 2007）。工程上不要用固定窗口，而用四条规则的“或”：

boundary = (precision * |observed - expected| > θ_pe)
        or topic_changed or person_changed
        or gap_seconds > θ_gap
        or duration_seconds > θ_max

θ_pe 由 2.4 的精度加权误差给出：误差越大、精度越高，越容易触发边界。θ_gap / θ_max 防止一段对话被切成无限碎片。分段后，事件继承参与者、话题、最大显著性、起始时间；文本只作摘要，原始感知仍保留。

实现口径这里的“图”不是图数据库，而是轻量关联索引：邻接表 + 1–2 跳扩展，每跳衰减、预算封顶；输出 path / hop，模拟边默认排除。它只用于候选扩展，不替代原打分。参考 runtime/graph_retrieval.py。
前沿补注提取不是中性的：目标提取会暂时抑制竞争项（retrieval-induced forgetting），也可能促进相关项；但 2024–2026 的直接证据仍有限。当前实现只做可逆、限时的可及性惩罚：命中后同话题/同人物的竞争项在 3 个逻辑时间单位内 ×0.85（默认按轮次；生产可配置为秒），TTL 到期恢复；不删证据、不改关系。
保护栏编码阶段不允许“边写边总结成事实”。事实与解释必须分开；摘要只能作为 summary 字段，不能替代原始事件。

5.2 提取闭环：从线索到情境包

  1. 线索解析。抽取人物、时间、地点、话题、情绪、目标；判断查询类型：事实、经历、关系、承诺、程序、还是“说不清”。
  2. 模式分离。先消歧：两个“张总”、两次“上次”、两版合同。相似度高于阈值但时间/场景/结果不同的，强制分成不同候选，并给出区分证据。
  3. 模式完成。从人物—事件—关系图做多轮扩展；向量近邻补充语义相似；时间与因果约束过滤。每一轮按 cue_overlap + association + recency + salience + source_reliability − interference 重排。
  4. 重建。把候选片段组装成一段连贯叙事，逐句标注来源 [E102]；事实与解释分开表述；不确定的地方明确说“不确定”。
  5. 来源审计。检查每一句的来源类型（亲历/转述/推断/生成）、证据数量、是否与已知记录冲突；给出整体置信度。
  6. 情境编译。把结果压缩成 4±1 槽位：who、relationship、experiences、goal、commitments、changes、uncertainties。每槽有 token 上限，超出则摘要或改为指针。

提取不是“把相关文档都找出来”。它是“为当前这一轮思考，选出最少但足够的几块”。如果情境包需要 20 个片段才能说清楚，通常说明系统没有巩固好，而不是主脑需要更多上下文。

5.3 决策闭环：主脑如何用情境包

  1. 定位。读情境包，确认：个体是谁、对面是谁、双方是什么关系、现在要做什么、有什么未完成承诺、有哪些不确定。
  2. 选模式。若情境签名命中习惯缓存，且风险低、时间紧、结果稳定 → 走 model-free 快路；否则走 model-based 慢路。仲裁权在主脑，不在后台。
  3. 推演。慢路中，主脑可调用未来模拟：基于相关情景生成 2–3 个可选剧本，比较预期结果、风险、关系影响；也可以要求后台展开某个事件或核查某条断言。
  4. 决定。主脑选择一个行动，并写下预期结果（用于之后的 RPE）。决定不需要后台“批准”，后台也没有批准权。
  5. 表达/行动。通过 Effector 执行：说话、发消息、调用工具、做出动作。Effector 只执行，不自行发起。

5.4 行动回写闭环：结果如何改变记忆

  1. 观察。记录实际结果、对方回应、副作用、是否达成预期。
  2. 算 RPE。δ = r − V(s)；正误差强化前一步，负误差削弱并标记“需要重新评估”。
  3. 更新事件。把事件状态从“开放”改为“已关闭/待跟进”；追加结果，不覆盖原记录。
  4. 更新关系。一次互动只作为一条证据；关系摘要按滑动窗口聚合，不因单次事件剧烈跳变（除非影响极大）。
  5. 更新来源校准。结果回写时调用 record_outcome：证实/推翻更新来源历史；结果作为直接事件写入；预测误差大时触发解释新版本；同一结果只算一条关系证据，重复回写不重复计入。
  6. 标记巩固。高显著性、高预测误差、未完成承诺的事件进入夜间巩固队列。

5.5 离线巩固闭环：睡眠做什么

离线巩固不是“把今天的对话总结一下”。它至少包含五道工序：

表 9 · 巩固批处理的五道工序
工序做什么对应机制
扫描遍历当日事件，按显著性 × 预测误差 × 目标相关 × 未完成度排序慢振荡的全局扫描
聚类按人物、项目、主题、时间把事件分组，选代表事件纺锤波的局部打包
重放对每组重放“前因 → 行动 → 结果”，生成反事实与教训海马涟漪的序列重放
抽象从多个事件中抽取图式、规则、技能候选；要求独立证据数达标系统巩固 / 图式同化
合并与修剪写入语义图谱/技能库；更新关系摘要；衰减低价值索引；压缩普通交互为阶段摘要突触稳态 / 自适应遗忘

巩固的优先级不是“最新的优先”，而是“最值得未来用的优先”：高显著性、高预测误差、与未完成目标相关、被反复访问但尚未抽象的事件，优先重放。相反，低价值、重复、无后果的日常交互，应该被压缩成阶段摘要，而不是逐条保留。

5.6 遗忘与再巩固闭环：安全地改变过去

这两个闭环常被混为一谈，其实方向相反：遗忘是降低可提取性，再巩固是更新内容。它们共享同一个触发点：提取。每次提取都记一次 access，但不增加证据数；如果提取伴随显著的预测误差或新信息，就创建新版本；否则只更新时间戳与可及性。

# 再巩固的极简判定
access_log.append(event_id, timestamp, cue, context)

PE = |expected_outcome − observed_outcome|
novelty = 1 − cos(new_info, existing_summary)

if PE > θ_pe or novelty > θ_novelty:
    new_version = revise(event, new_info, basis=evidence_ids)
    new_version.supersedes = old_version.id
    store.append(new_version)          # 不覆盖旧版本
    enqueue_for_consolidation(new_version)
else:
    event.last_accessed = now
    event.access_count += 1            # 只提升可及性，不增加证据

遗忘则按保留率公式执行：R = exp(−Δt / S) × (1 + α|valence|) × (0.5 + 0.5·utility) × relationship_factor。低于阈值的内容移入冷归档；低于更低阈值且不属于豁免清单的，移除活跃索引。原始事件日志仍然保留，供审计与“被遗忘权”之外的合法追溯使用。

5.7 闭环之间的耦合：不能单独优化任何一环

六个闭环不是流水线，而是相互咬合的回路。只优化其中一环，通常会把问题推到另一环：

  • 编码 ↔ 提取。编码时没有留线索，提取时就会“想不起来”；提取失败的模式，应该反哺编码策略，告诉系统“下次这类事件要记什么”。
  • 提取 ↔ 巩固。被反复访问却始终没有抽象的事件，是巩固的优先候选；反之，从未被访问、也无未来效用的事件，应该更早进入冷归档。
  • 巩固 ↔ 编码。巩固形成的图式，会改变下一次编码的显著性：与图式一致的信息更容易被快速合并，不一致的信息则值得更深地写入。
  • 遗忘 ↔ 提取。遗忘降低干扰，让检索更准；但遗忘过度会让系统“重新发现”已经学过的教训。保留率公式与豁免清单，就是这两者之间的调节阀。
工程含义不要用“检索命中率”单独考核系统。一个只优化检索的系统，会倾向于保存一切、拒绝遗忘；最终上下文变脏、决策变慢。闭环的指标必须成对出现：召回率配精确率，保留率配误删率，压缩比配信息损失。
