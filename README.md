# 多模型双脑记忆系统

**从神经机制到多模型模拟方案**

版本 2.1 · 2026

> **状态：思路稿。**  
> 本仓库记录的是一条构建思路，不是已落地的框架、产品，也不是经过验证的实践。文档讨论记忆、关系与多模型分工可以如何组织，不声称已经给出完整架构或实现。`runtime/` 只是对部分契约的参考探针，不代表框架本身。

> **文档题名说明：** 正文 HTML/PDF 保留原题《双脑记忆系统：从神经机制到多模型模拟方案》；仓库使用更简洁的项目名。

## 为什么做这套方案

**1. 单模型装不下“一个连续的人”。**  
一个人的连续存在，不是一次对话，而是长期的关系、承诺、共同经历。把全部历史塞进上下文，既昂贵，也会让判断被无关信息稀释；只做向量检索，又只能得到“相似片段”，得不到“这个人是谁、个体与他是什么关系、彼此答应过什么”。这套方案想验证：能不能让主脑每轮只读一个很小的情境包，但这一块足够做出判断。

**2. 记忆的理由是关系，不是存档。**  
人是社会性动物，记忆帮助个体认清自己与他人的关系与地位。共同经历把人物与事件连接起来：看到一个人，会想起相关的事；想起一件事，也会想到参与其中的人。人物与事件的对应，是人与人的关系原点，也是记忆存在的理由。关系不是单一维度：在关系维度里，保留率只看情感强度，不看信任；情感强度低，相关记忆才容易淡化，亲近或憎恨越深，相关经历越深刻。信任与能力决定承诺；边界单独维护。不能把“亲近”当成“可信”。承诺要留，解释可改。保留率不是只看时间/频率：可靠来源的复现提高稳定度，情感强度决定相关记忆的深浅，未来效用与关系强度共同调节；未完成承诺不衰减。只存对话、不按关系组织，它就只是日志，不是“记得一个人”。

**3. 多模型不是多 Agent，是同一个体的器官。**  
现有 agent 框架通常把任务拆给多个 agent，各自有目标、工具、行动，最后像委员会一样协商。这套方案想模拟的不是“一群 agent 开会”，而是：多个模型像脑的不同功能单元，分别处理人物识别、记忆检索、关系判断、情境整理；它们只准备情境，不替个体决定；最后只有一个整合中心——它属于整个有机体，不是主脑进程。重点不是“多”，而是“多而一”。

**4. 现有方案缺的不是记忆，是“关系的连续性”。**  
只存对话，不存人物—事件—关系；只做相似检索，不区分事实、解释与承诺；只服务单次任务，不服务跨时间的连续关系；多模型协作容易变成委员会，没有唯一负责的整合中心。这套方案要补的，是关系与判断的连续性，而不是再建一个更大的向量库。

**5. 想验证的假设。**  
如果记忆按人物—事件—关系组织；上下文只给此刻关系与承诺的切片；后台只做情境准备，不提供建议、不代替决定；多个模型分工，但只有一个整合中心；那么，一个模型群可能在小上下文下表现出连续的个体感，而不是每次重新认识。这只是一个假设，不是已经落地的框架，也不是经过验证的实践。

|---|---|

| `source/en/build.py` | 从 `source/en/parts` 构建英文 HTML |

cd runtime

## 这不是什么

- 不是框架：文档描述的是一条思路，不是完整架构。
- 不是产品，也不是经过验证的实践；不声称可生产部署。
- 不是临床或神经科学结论；神经科学用于解释设计理由。
- `runtime/` 不是生产系统：没有真实持久化、签名密钥、分布式写入或生产级批准账本。
- API 与 schema 不稳定；它们只是让部分契约可测试、可审查。
- 仓库不包含 GitHub token、QA 渲染图或临时构建产物。
